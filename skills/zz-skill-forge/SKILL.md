# zz-skill-forge · 技能工坊

## 一句话

从一句需求到一份能跑的技能稿。

## 用与不用

适合用的场景：

- 用户反复做同一类事，想固化成技能，以后一句话就能触发
- 已有技能触发不准、步骤含糊、产出不稳定，要动手改
- 用户口述了一套自己的工作流程，想变成 Agent 能执行的指令
- 同一类活换个人做就变样，想把做法定成统一标准
- 技能要交接给别人维护，需要补结构和验收标准

不该用的场景：

- 一次性任务，做完就不干了，不值得做成技能
- 依赖外部 API 密钥、环境部署的工程活，先把环境搭好
- 用户只是想找个现成技能用用，那是检索，不是造

## 开工前要什么

必需信息：

- 这技能解决什么问题
- 什么情况下该想起它：用户会说什么话来触发

可选信息：

- 目标环境对技能格式的要求
- 要改的是哪个已有技能，毛病出在哪
- 一两个真实的完整案例：当时输入什么、想要什么产出
- 一份用户满意的成品样例，比如他交上去没挨批的那期周报

用户没给时的默认假设：

- 没说格式，就按「YAML frontmatter 加 Markdown 章节」的通用
  结构写
- 没有真实案例，就让用户口述最近一次的完整做法补位
- 技能名沿用用户起的；没起，就按「这件事是干什么的」取个短名

## 怎么做

1. 澄清触发场景
   - 做什么：问清什么话进来该加载这个技能，什么话不该
   - 判断标准：能写出至少 3 条触发词和 1 条不该触发的情形
   - 中间产物：触发清单

2. 收一个真实案例
   - 做什么：让用户完整讲一遍实际做法：输入什么、过程怎么走、
     产出长什么样
   - 判断标准：案例里有具体对象和数字，不是「大概整理一下」
   - 中间产物：案例素材

3. 定结构
   - 做什么：按目标格式列章节骨架，通常是何时用、怎么做、
     交付样式、红线
   - 判断标准：每一章都有明确用途，可有可无的章节直接砍
   - 中间产物：目录骨架
   - 结构骨架直接从本仓库 `_template/SKILL-template.md` 复制修改，写作规范见 `_template/写作规范.md`，保证新技能符合全库九段规范。

4. 成稿
   - 做什么：每一步写清「做什么加判断标准」，把第 2 步的案例
     贯穿全文当示范
   - 判断标准：拿案例照着稿子走一遍，不卡壳
   - 中间产物：技能草稿

5. 试跑
   - 做什么：换一个新输入，严格照稿执行一遍
   - 判断标准：产出符合用户预期；每个步骤无歧义，执行者不用猜
   - 中间产物：试跑记录，写明用的输入和发现的问题

6. 验收修订
   - 做什么：对照验收清单逐条核，改完再试跑一次
   - 判断标准：验收清单全部通过，两次试跑结果一致
   - 中间产物：终稿加验收记录

7. 导出多平台版本
   - 做什么：把同一方法压缩成 Grok Bot 人设提示词版（system prompt 形态）/
     Coze（扣子）智能体版（工作流+提示词结构）/
     单页说明版，方法内核与触发词、红线保持一致
   - 判断标准：导出版在任何平台独立使用时不丢失触发词和红线
   - 中间产物：导出文件

## 交付长什么样

背景：用户想造一个周报技能。他说：「每周写周报都头疼，流水账
一大堆，领导老批没重点。帮我做个技能。」上周小林的周报就被批了
「没重点、看不到需要什么支持」。

交付是两个东西：技能终稿，加一份验收记录。

技能稿骨架（节选）：

```markdown
---
name: weekly-report
status: stable
description: 当用户说「写周报」「把本周工作整理成周报」时用。把
流水账提炼成一页周报：先圈 3 件最重要的事，每件写结果和下一步，
末尾汇总需要的支持。触发词：周报、本周总结、weekly。
---

# weekly-report · 周报助手

## 怎么做
1. 收流水账：让用户把本周做过的事随手丢出来，不用整理
2. 圈重点：请用户从流水账里圈 3 件最重要的事
   - 判断标准：用户圈完才往下走；用户不想圈，就按影响的人数
     和金额提出 3 件候选，让用户点头
   - 中间产物：3 件事清单
3. 每件事写三行：干了什么、结果（有数字带数字）、下周动作
   - 判断标准：不许有「持续推进」这种没法检验的表述
4. 末尾一栏「需要的支持」：照实写，没有就写「无」
   - 判断标准：小林上次被批「看不到需要什么支持」，这栏
     不许漏

## 交付长什么样
一页周报：标题带日期，3 件事每件三行，末尾「需要的支持」。
别加感想和流水账，领导要的是重点。
```

验收记录长这样：

```text
【试跑一】输入：小林本周流水账 9 条（改 bug、开会、面试新人等）
发现的问题：
  1. 第 2 步直接挑了 5 件事，用户嫌多 → 改为固定 3 件
  2. 产出漏了「需要的支持」栏 → 补第 4 步，并写成判断标准
【试跑二】同一输入重跑：3 件事、每件三行、支持栏齐全。
用户确认：「这版能直接交。」
【验收清单】
- 触发描述有 3 条触发词和 1 条不该触发的情形 …… 通过
- 每步含做什么加判断标准 …… 通过
- 案例贯穿全文，有具体对象和数字 …… 通过
- 两次试跑产出一致 …… 通过
【结论】终稿可交付，路径 skills/weekly-report/SKILL.md
```

## 红线

- 技能必须有触发描述：何时用加触发词。没有触发描述不许算完工
- 每个步骤必须含「做什么加判断标准」，只有动作没有标准的步骤
  退回重写
- 必须至少试跑一次，试跑记录要写明用的输入和发现的问题，
  没有试跑记录不算交付
- 不编造技能没验证过的能力。没试过导出 PDF 就不能写「支持导出」
- 与已有技能重名或功能重叠时，动手前先向用户指出重叠部分
- 导出多平台版本时不得删除触发词与红线，导出前逐项核对

## 常见坑

- 一上来就写文件，触发场景没问清，做出来 Agent 不知道什么时候用
- 步骤全是「分析、整理、优化」这类空动词，执行的人没法下手
- 把一次性特例写死进技能，换个场景就不适用。案例当示范，别当
  唯一模板
- 从不试跑，看着「没毛病」就交付，实际一跑就卡
