# zz-fact-first · 事实优先说明文

## 一句话

先讲改了什么，再讲跟你有什么关系。

## 用与不用

适合用的场景：

- App 发新版本，要写应用商店的更新说明
- 功能上线，要给用户讲清楚这功能是干嘛的
- 修了故障，要在公众号或用户群里交代
- 写 changelog，团队内部和对外都要一份
- 固件、SaaS 后台改了东西，要写进版本公告

不该用的场景：

- 品牌广告、活动海报——那是营销文案，目的不一样
- 还没定稿的功能——写了也白写，功能随时会变
- 事故问责报告——那是给内部查原因的，不是给用户的
- 融资稿、招聘稿这类要情绪动员的文字——事实顺序撑不起来

## 开工前要什么

必需信息：

- 这次改了什么，逐条列：新功能、修复、调整、下线
- 每条改动影响哪些用户：全部、部分，还是某个平台
- 版本号和上线时间

可选信息：

- 改动前后的数据对比，比如加载时间、步骤数
- 改动的原因，修复类的尤其要有
- 用户之前有没有催过这个功能，催过的可以点名回应
- 这次没来得及做的事项，方便顺手交代

用户没给时的默认假设：

- 没给数据对比，就不写数字，不猜
- 没说影响范围，按"全部用户"写，并在交付里标注这是假设
- 没说渠道，默认出应用商店短版加一份长版

## 怎么做

全程用一个例子跟走：一个记账 App 发 v3.2，开发给了三件事——新增账单搜索（按备注、金额、日期搜，以前只能按月翻）；修复部分安卓用户周三凌晨闪退（定时任务冲突）；首页加载从 2.1 秒降到 0.8 秒。

1. **收事实清单**

   - 做什么：找开发或产品逐条确认：改了什么、为什么改、影响谁、哪天上线。
   - 判断标准：每条都有动词和对象，"优化了体验"这种不算一条事实。
   - 中间产物：事实清单。本例 3 条，全部带具体对象。

2. **按用户排优先级**

   - 做什么：用户最常碰到的排最前；修崩溃的排在新功能前面还是后面，看影响面。
   - 判断标准：排序能说出理由，比如"搜索全员可用，闪退只影响部分安卓"。
   - 中间产物：顺序稿。本例排序：搜索第一，闪退第二，加载第三。

3. **每条写两句**

   - 做什么：第一句写改了什么，动词加对象；第二句写对你意味着什么，给场景和前后对比。
   - 判断标准：影响句里有具体的使用场景，不是"提升效率"。
   - 中间产物：两句稿。本例搜索写成——"账单能搜了。搜备注、金额、日期都行，找账不用再一页页翻。"

4. **删包装词**

   - 做什么：对照包装词表逐个检查并删掉：全新升级、更智能、极致、贴心、赋能、流畅体验、一站式、重磅、焕新。
   - 判断标准：删掉包装词后，句子的信息量一点没少，才算删干净。
   - 中间产物：净化稿。本例初稿里的"全新升级"和"更智能"各删了一处。

5. **数字定源**

   - 做什么：每个数字问来源——实测、估算还是内部统计，来源标注在稿子末尾。
   - 判断标准：写不出来源的数字，直接不用。
   - 中间产物：定数稿。本例"2.1 秒降到 0.8 秒"标注为内部实测均值。

6. **按渠道出稿**

   - 做什么：商店版压到 100 字以内；公众号长版每条两三句；changelog 只留要点。
   - 判断标准：每个渠道的字数和格式，符合那个发布位的要求。
   - 中间产物：渠道稿。本例出了三版。

7. **终检**

   - 做什么：对每条问一句"用户读完能做一件以前做不了的事吗"。
   - 判断标准：有一条答不上来，就把那条打回第 3 步重写。
   - 中间产物：成稿草稿。

8. **交代没做的**

   - 做什么：把这次没来得及做、但用户在等的事，单独列一小节说明。
   - 判断标准：只列事实和下一步时间，不甩锅、不画饼。
   - 中间产物：待办说明。本例加了一句——"账单导出 Excel 还在排期，预计下个版本。"

## 交付长什么样

```
【应用商店版 · 98 字】
v3.2 更了三件事：
1. 账单能搜了。搜备注、金额、日期都行，找账不用再一页页翻。
2. 修好了部分安卓手机凌晨闪退的问题。
3. 首页打开快了：加载从约 2 秒降到 1 秒内。

【公众号长版】
v3.2 更新说明

一、新增账单搜索
改了什么：账单列表加了搜索框，备注、金额、日期都能搜。
对你的影响：以前找一笔账要按月份一页页翻，现在搜"打车"，
直接看到今年所有打车记录。

二、修复凌晨闪退
改了什么：修好了部分安卓用户周三凌晨两到五点闪退的问题，
原因是后台一个定时任务冲突，已经解决。
对你的影响：如果你之前遇到过"早上打开 App 发现昨晚没记上的账"，
升级后不会再出现。

三、首页加载变快
改了什么：首页加载时间从约 2.1 秒降到 0.8 秒。
对你的影响：打开就能记，不用等转圈。

数据来源：加载时间为内部实测均值（同一批测试机，20 次取平均）；
闪退范围为崩溃上报统计，覆盖约 3% 的安卓用户。

【changelog 版】
v3.2
- 新增：账单搜索（备注 / 金额 / 日期）
- 修复：部分安卓设备凌晨定时闪退
- 优化：首页加载 2.1s → 0.8s
```

## 红线

- 每条功能点的第一句以动词加对象开头，比如"新增账单搜索""修复闪退"，不许以形容词开头
- 全文不出现这些词：全新升级、更智能、极致、贴心、赋能、流畅体验、一站式、重磅、焕新
- 每个数字都有来源标注，写不出来源的数字不用
- 影响句必须落到具体场景——什么时候、干什么的时候用得上；只写"提升效率"不合格
- 版本号、日期、上线状态与事实一致，没上线的功能不许写成已上线

## 常见坑

- "修复若干问题，优化用户体验"——用户看完什么也没知道，修复要写清修的是什么
- 影响句写成第二个包装句，比如"让你效率飞升"——影响句要说场景，不是换着法夸自己
- 所有更新点平铺不分主次。用户只看前两条，重要的排在后面等于没发
- 内部术语直接端给用户。"重构了缓存策略"用户听不懂，先翻译成"打开快了"再写
